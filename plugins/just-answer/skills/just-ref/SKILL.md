# 找 reference

使用者想知道「某個功能或需求，在文件的哪裡有寫」，並且要能自己回頭核對。價值在於「引文一字不差、位置找得到」：憑記憶給的章節或引文看起來可信但常是錯的，使用者拿去引用就出事，所以一律要實際讀到來源文字才能引。

這個 skill 只負責找 reference，不解釋、不摘要、不評論。

## 輸入

本次指令附帶的文字 = 來源（可省略）+ 功能描述。呼叫時沒有附帶文字，就等待使用者提供。

- 開頭連續幾段是實際存在的檔案或目錄路徑（含 `$HOME\...`、`~`、相對路徑；含空白的路徑會加引號）→ 本地來源，其餘為功能描述。
- 否則 → 線上文件。若開頭是文件名稱（如 `RFC 3261`）就以它為來源，其餘為功能描述；沒指定來源（如只寫 `SIP fork`）就自行判斷最權威的來源，在輸出標明規格名稱與版本，不反問。涉及多份規格時各自找候選。

## 一定要讀到原文

- 線上：用網頁搜尋與抓取工具，讀到該規格的官方或公開全文，在抓回的內容裡找到段落。
- 本地：用讀檔工具讀。PDF、docx 等用對應的 skill 或轉文字方式；檔案大時先搜尋定位，再讀候選段落周邊確認，不整份硬吞。
- 引文與位置只能來自這次實際讀到的文字。讀不到就是讀不到，不用記憶補。
- 網頁抓取工具常會把內容先交給小模型摘要，回傳的「引文」可能已被改寫，不能直接當原文。能下載全文（如 `curl` 存到全新的空目錄）時，用固定字串比對確認每段引文真的出現在全文中（先把換行與連續空白壓成單一空白再比）；比對不到的引文不能用。下載不了、只能靠抓取工具回傳時，在該筆引文後標「（未逐字核對全文）」。

## 本地多檔與目錄

使用者的專案常混雜 pdf、docx、圖片，也可能直接給整個目錄。

- 目錄：遞迴列檔，只讀可讀的文件類型（pdf、docx、xlsx、pptx、md、txt、html、圖片等），略過建置產物、`.git`、二進位等無關檔。
- 檔案多時先用檔名與目錄結構縮小範圍，再搜尋文字定位。
- 某檔讀不出來（加密、損毀、掃描檔無文字層）時，在輸出最後單獨一行寫「未能讀取：<檔名>、…」。不能默默略過，否則使用者會誤以為這些檔案已涵蓋在內。
- 圖片靠視覺讀取，文字無法被搜尋，引文後標「（圖片文字，視覺辨識，請人工目視核對）」；看不清的字就不引。

## 引文

引文的用途是讓使用者 Ctrl+F 搜得到，所以要和來源逐字相同：

- 取實際讀到的連續一段原文，不改寫、不翻譯、不把不相鄰的句子接起來、不用「…」跳過中段。需要節錄就只取一段連續片語或句子，長到足以辨識，但不整段貼。
- 保留原文語言：用中文問英文規格，引文仍是英文。
- 保留原標點、大小寫、用字。PDF 的換行與行尾斷字還原為原本拼法，只處理換行造成的差異。
- 引文用引號框住，放在位置之後獨立一行，不混入說明。

## 位置

- 規格與標準：`<名稱與版本> §<章節編號> <章節標題>`，有頁碼再加 `p.N`，並分清是文件印刷頁碼或 PDF 檢視器頁碼。
- 合約、RFP、SRS 等本地文件：檔名（目錄來源時為相對路徑）＋條款或章節編號＋標題；有頁碼加頁碼。
- 線上附實際開過的連結，能指到錨點就指到錨點。
- 看不出章節就只標頁碼，或不標；不寫「大概在某章」。

## 學術來源

論文、期刊等學術來源，用 APA 7 格式描述來源，引文後標頁碼，沒有頁碼就標章節標題。規格、RFC、合約等非學術文件不套 APA，用上面的位置格式。細節讀 `references/source-handling.md`。

## 排序與數量

依符合度由高到低排。符合度的判斷：直接定義或規範該功能的，優於只是提到的；規範性條文（shall、MUST、「應」）優於說明、範例、註解；定義處優於引用處。

排序就是符合度的全部表達，不另寫分數、理由或說明這段在講什麼——使用者看原文自己判斷，這樣不會混進模型的詮釋。預設給 3–5 筆；只有一個明確答案就只給一筆，不湊數。

## 讀不到原文時

付費、需登入、搜尋不到全文時，可以用二手來源，但限制比一般嚴格：引文必須取自該二手來源實際出現的文字，章節位置要有至少 2 個獨立來源一致才能標。完整規則與格式讀 `references/source-handling.md`。

完全找不到可用內容時，用一句話說明查無，並說明查過哪些來源；不拿相近內容充數。

## 輸出格式

```
1. <來源名稱與版本> §<章節> <標題>（p.N）<連結或檔名>
   > "<一字不差的原文>"
2. ...
```

- 區塊外不寒暄、不總結、不評論；唯一例外是本地來源有「未能讀取」時的那一行，以及二手來源標註。
- 候選來自多份文件時，每筆位置都標明來源。
