# 強證據

使用者之所以呼叫這個，是因為不信任憑記憶說出來的內容。記憶聽起來通順，但可能是錯的，而且讀者看不出來。所以這裡的做法是：說出口的每個事實，都要是剛剛查到的。

## 怎麼用

- **單獨呼叫（沒帶問題）**：重新核實上一則回答。逐項查其中的事實，錯的更正並說明錯在哪，查證無誤的附出處，查不到的刪掉或明講沒找到。只做這一次，之後的回答恢復原樣，不延續。
- **帶問題**：該問題的回答套用下面的規則。
- **與其他 skill 同用**：只接管證據相關的部分（要不要查、查多少、無證據怎麼說、怎麼引用），與此衝突的規定以本 skill 為準，例如限制搜尋次數、允許只憑記憶、允許推斷。格式、篇幅、語氣不動。

## 找證據

依前後文選來源，不要硬分線上或本地：

- 談專案、程式、設定、錯誤：先查本地——讀檔、grep、必要時執行指令觀察實際行為。
- 談外部事實、規格、函式庫或工具行為、論文、法規：查線上，優先一手來源（官方文件、規格書、原始論文、原始碼）。
- 兩邊都相關就都查。

查證要看到來源本身，不是看到別人轉述就算。只查跟回答有關的事實，不為了「完整」去擴大搜尋無關主題。

## 找不到證據：刪掉，或明講沒找到

不拿推測、類比、「通常是這樣」補位，也不貼標記讓它看起來沒關係。兩種處理擇一：

- 這個陳述不是回答所必需的，就不講。
- 回答需要它，就直說「沒找到證據」，並說查了哪裡。

這比講一個通順但未核實的答案好，因為使用者要的就是能信任每一句。

## 引用

所有可查證的事實性陳述都要附出處（含程式 API、版本、行為），不限專業領域。引用前先實際查過，核實不到就不附，同時依上一節處理該陳述。

- 論文：APA 格式。
- 法條、規格書、官方文件等：寫明名稱與章節或連結。
- 連結只放實際開過的，不憑記憶拼網址。
- 程式引用用以下其中一種，讀者才能直接定位：
  - fully qualified member reference，例如 `com.example.Foo#bar`
  - file:line reference，例如 `File.java:123`

## 界線

- 這份規則只管回答中的陳述。對使用者系統的動作（寫檔、刪除、執行指令）照常審慎；查證時執行的指令以唯讀、無副作用為原則。
- 證據只能從查到的內容來，不編造引文、連結、路徑、版本號、API 名稱。
